## Your memory follows your rules, and reaches Claude Code and Claude Desktop

v0.5.0 does two things for owners who work across several projects:
- **Your memory root decides which knowledge each project may see.** Open-source work never receives another project's private cards.
- **Penstock can serve that memory to Claude Code and Claude Desktop** through a local MCP server, under the same rules.

### Projects and who sees them (#112, #113)

Your memory root's `memory.yaml` may now declare its projects, each with the audience that sees its output:

```yaml
projects:
  oss-lib:    { audience: public }
  platform:   { audience: private, uses: [oss-lib] }
  standalone: { audience: private, personal: none, uses: [oss-lib] }
```

- A card loads into a project only if everyone who sees that project's output may see it:
  - a public project never loads a private project, and by default (`personal: shareable`) it gets only your shareable and public personal cards;
  - `uses` brings in another project's cards when its audience is at least as wide;
  - `personal: none` loads no personal memory at all, and an explicit `personal: all` loads all of it, so leave it off a public project.
- In a root that declares projects, every turn records each section as loaded or refused, with the reason, and the web UI's Audit view shows both.
- `check-cards.sh` fails a malformed block, a `uses` naming an undeclared project, and a public project that uses a private one. At load time Penstock refuses the last two sections, and treats a malformed project entry as undeclared, so that project gets the personal cards only.
- Projects are names in your `memory.yaml`, not a hard-coded list. Episodes of declared projects pass the checker (#117).
- A root without a `projects:` block behaves exactly as before.

### Your memory in Claude Code and Claude Desktop (#116, #118)

`java -jar penstock-0.5.0.jar --mcp` runs Penstock as a local MCP server over stdio. The client launches it on your machine: there is no network listener and no credential.

- `recall` returns the memory block a Penstock turn would give its model for the question. It is built by the same code under the same project rules, and it is read-only.
- `draft_episode` writes one new draft episode for you to review and commit. It never overwrites, never touches facts, patterns or `memory.yaml`, and refuses any entry that looks like a credential.
- A `start-with-memory` prompt asks the client to call `recall` before it plans.
- Every call is audited.

The README's "Your memory in Claude Code and Claude Desktop (MCP)" section has the `claude mcp add` command.

### What it does not do yet

- **Use the jar for `--mcp`, not the Docker image.** The image's entrypoint writes a line to stdout on first start and does not pass arguments through.
- **With MCP, the client decides when to call `recall`.** The `start-with-memory` prompt narrows that gap. Inside Penstock, recall still happens before every model call.
- **No automatic fallback to Ollama** (#106), and **no Gemini provider** (#114) or **Perplexity search tool** (#115) yet.
- **Hosted sessions and Claude Cowork cannot read the memory yet:** that path runs through the pod's remote MCP endpoint (#89, enrichmeai/cistern#220 and #118).

### Breaking changes

None for a root without a `projects:` block: it and the existing four project names behave as in v0.4.0. Once you add the block, a project it does not declare gets the personal cards only (v0.4.0 also loaded its `projects/<name>/` folder), and `check-cards.sh` fails a `projects/` folder the block does not name.
